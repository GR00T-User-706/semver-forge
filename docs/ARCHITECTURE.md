# Architecture

SemVer Forge separates semantic-version policy, repository operations, project-file
synchronization, and its own diagnostics.

## Core layers

- `semver.py`: strict SemVer parsing, precedence, and increments.
- `conventional_commits.py`: commit-message parsing and release-impact classification.
- `release.py`: release planning and local release orchestration.
- `version_sources.py` and `synchronization.py`: canonical version reading and metadata synchronization.
- `vcs.py`: version-control backend protocol and selection.
- `git.py`: first backend, implemented with safe argument-array subprocess calls.
- `operation_log.py`: bounded local diagnostics for SemVer Forge itself.

## VCS support

Git is currently the only implemented backend. Mercurial, Subversion, Fossil,
and Perforce are potential future adapters, not supported backends today.
Project initialization and version configuration do not require a VCS.

## Logging boundary

The internal diagnostic log defaults to
`$XDG_STATE_HOME/semver-forge/semver-forge.log`, or
`~/.local/state/semver-forge/semver-forge.log`. It is bounded to 10 MiB and
retains the newest entries. It is not a project log: SemVer Forge does not
discover, create, ignore, stage, commit, or untrack project-maintainer log files.

## Initialization

Initialization writes generated files using temporary files and atomic replacement.
Only files generated by the current invocation are staged. Automatic commit is
skipped when the Git index already contains staged changes, protecting unrelated
staged work. A failed commit leaves generated files in place and reports the
recovery state. A push is attempted only when a remote is configured; push failure
does not undo the local commit.
